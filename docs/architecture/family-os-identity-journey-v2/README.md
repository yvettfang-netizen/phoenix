## Service contract

1. Resolve an authenticated Family OS person and family to existing Canonical identifiers. For a different subject, recheck verified scope and capacity. For an adult delegate, require a separately approved subject-bound authorisation. A sponsor relationship and the dependant's own immigration status are distinct.
2. Record a person's distinct periods, case facts, document types and date revisions. `VISA_ISSUED`, `FIRST_ENTRY_DEADLINE`, `FIRST_ENTRY_ACTUAL`, `STAY_EXPIRY`, `RENEWAL_WINDOW_OPEN` and `RETURN_BY` are independent. Preserve verified records and the supersession chain. Keep actual file content and identifiers in the controlled Docs model.
3. Schedule configurable offsets in `Asia/Hong_Kong`. Only use a verified case source for an approved expiry or an official window. Internal suggestions and airport/travel reviews carry their own basis. Reconcile the old revision and new jobs atomically. Lock one due row, recheck purpose, grant, source revision and authorized recipient, then record one in-app notice with one idempotency key. Persist retry state on transient failure without clearing existing receipts. Revocation cancels pending notices and denies historical private details. External channels require independently reviewed authorization and successful delivery receipt. The code currently covers planning, reconciliation and the adapter contract.
4. With an explicit client request and separately approved consultation permission, emit only the three-field summary `{domain, topic, horizon}` plus an authoritative internal correlation reference. Recheck exact consent before downstream write and on retries. Use the existing CRM client/lead and approved acquisition contract. Do not pass exact dates, travel history, evidence references or passport/ID numbers. `IDENTITY_CASE / IDENTITY_SENSITIVE` authorizes only the purpose of the existing grant and cannot itself be repurposed for CRM or external notification.
5. Confirm signed contract using the authoritative contract service and then use existing Service Project management. Retain the same canonical client and explicitly authorized project subject. A verified new Individual status date is written by an authorized operator with an audited source. This supersedes the old date and recomputes station reminders. A Service Project status alone never verifies an expiry or an official decision.
6. Send only purpose-bound, aggregated counts to the internal 观澜台 projection. Buckets are 0–90, 91–180 and unknown. No member, exact date, case-level or travel details are required. Apply the approved small-group policy before exposing counts. Retract revoked data from projections.

## Residence and documents

The helper uses half-open local-date intervals. Overlaps are deduplicated and disagreements, gaps and unverified segments stay in a review bucket. The result reports recorded physical presence and recorded absence, never a legal finding. A reference planning date, when agreed, is separate from any application deadline. Hong Kong birth, lawful admission, ordinary residence, permanent resident card, right to land, unconditional stay, travel document and passport eligibility remain separate concepts. Individual decisions require verified case evidence and professional review.

The residence panel uses the existing Family OS sign-in. It accepts a completed Hong Kong civil-date interval, a location class, an optional reason category and an optional planned return. Read and report authority are separate binds. The report uses the existing Canonical person and case and rejects shared-family access to another person's record. Adviser confirmation is a separate database operation that requires an active assignment plus Identity Case and Docs consent. It pins a specific Docs version and appends a confirmation while keeping the original report. The applicant screen exposes the verification source and interval only.

## Verification and limits

- The code and workflow test reminder offsets, leap day/Hong Kong time, verified vs reported dates, multiple family members, renewal rescheduling, revocation, idempotency, retry and minimised CRM summary projection.
- The PG16/PG17 workflow starts disposable containers, runs the unchanged 37 formal migrations, checks that the candidate refuses the baseline database, then validates the candidate and rolls back synthetic data. No application, reader or public role can access candidate tables.
- The public demonstration uses synthetic data and does not persist user entries. The authenticated residence and consultation candidates exercise persistence with isolated PostgreSQL, synthetic sessions and distinct authorization fixtures. The target runtime bindings, official record source and professional review remain release gates.
- The complete 18-scenario matrix requires live-authorized acceptance of multi-status history, CIES and Hong Kong birth journeys, delegated adult access, overdue notices, verified document/eligibility review and at least one real authorized run through CRM → contract → Service Project → identity date → station reminder → aggregate. Candidate tests and fixtures are not evidence of that connected flow.

The shortlist for the next candidate is a governed appointment of owner/roles for the signed contract authority, per-purpose consent (read/write/reminder/consultation), worker receipt and Canonical DTOs, and a reviewed identity evidence-retention policy and audit surface. No production switches or data changes are part of this branch.
