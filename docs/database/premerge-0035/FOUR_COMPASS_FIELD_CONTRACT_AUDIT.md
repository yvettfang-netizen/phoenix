# Four Compass field contract audit

**FOUNDER PRODUCT TAXONOMY CONFIRMED / DATABASE IMPLEMENTATION PENDING.** Founder instruction `PHOENIX-CANONICAL-0035-PR36-CLOSEOUT-20261102` confirms the taxonomy below. Source SQL: private Canonical commit `3af6ba19a96a458dc20cb0f4493bed10aee7028a`, 0027–0034. This is a code/contract audit, not a production-data inspection.

The four professional domains are `EDUCATION`, `IDENTITY`, `WEALTH` and `HEALTH`. `CHILD_COMPASS` is the child-growth entry within Education; `FAMILY_COMPASS` is a cross-domain family-planning entry. Neither entry is a synonym for Identity or Wealth. In particular, **FAMILY_COMPASS must never be rewritten or inferred as WEALTH_COMPASS**. The database must preserve three distinct facts: (1) product/channel of entry; (2) professional need explicitly selected by the user or confirmed by an advisor; (3) the service eventually consulted or sold.

Current SQL stores entry in `crm.lead_attributions.compass_kind` with `FIRST_TOUCH`/`CONVERSION_TOUCH`; consultation domain in `crm.consultations.business_domain`; commercial and delivery domains in `crm.deals`, `crm.deal_items`, `service.projects` and `service.project_domains`. `crm.leads` has no explicit professional-need domain; `crm.consultations.business_domain` does not by itself prove whether the user selected a need or an advisor confirmed it. A **separate forward 0036+ design** is therefore needed for an explicit, attributed need fact and its audit trail. This PR does not contain that Migration.

The final-integration goal also requires exact direct entry from Identity and Wealth professional pages. The mandatory 0032 attribution column and current create-lead API accept only the four legacy entry values. They cannot satisfy this requirement by substituting `FAMILY_COMPASS`; the separate additive design must preserve the real page/product and its version without inventing new approved codes.

The existing First Touch is immutable historical attribution for this decision: do not revise its `compass_kind`, source or timestamp to represent later need or service changes. Do not edit 0032 or 0033. A later user/advisor need and final service must be recorded in their own fields/events, with synthetic checks for `CHILD_COMPASS`→Education and `FAMILY_COMPASS`→Identity/Wealth/Health without attribution overwrite. The separate private [compatibility/design Draft PR #8](https://github.com/yvettfang-netizen/phoenix-canonical-db/pull/8) contains no new executable Migration; its synthetic test fixtures and interface preparation are outside public PR #36.

The existing `Phoenix Compass` application folders in `phoenix/main` are implementation assets, not an approval of the database `compass_kind` code list. The Health Compass persistence gate remains separate from the generic `HEALTH` business-domain value.
