# Canonical Service Project staging database package

This package is an operator-run database rehearsal for a dedicated empty database. It does not create a database, provision a host, deploy an application, change DNS, enable customer access, or import real data.

The target is fixed to `phoenix_service_project_staging` on PostgreSQL 16 or 17 at `localhost`, `127.0.0.1`, or `::1`. The preflight refuses a non-loopback host, a production environment variable, a different database name, unknown SQL, a changed historical SHA, a changed 0040 Identity build-inventory file, a non-empty database, or a partial ledger. The current pinned 0040 candidate is `database/canonical/forward-candidates/service-workbench/0040_hk_identity_workbench.sql` with SHA-256 `fc3fa2c2125e7e94c73b938a34f60ebcc893e2de748757047e05855a3c69b19e`.

Run the read-only checks first from the repository root.

```text
ops/service-project-staging/db-preflight.sh \
  --user <staging-operator> \
  --identity-sql <path>/0040_<identity-build-inventory>.sql \
  --identity-sha256 <exact-64-hex-sha>
```

The apply step is separate and requires the explicit `--confirm-staging` gate. It applies the 40-file plan in order, using one transaction and one ledger row per file.

```text
ops/service-project-staging/db-apply.sh \
  --confirm-staging \
  --user <staging-operator> \
  --identity-sql <path>/0040_<identity-build-inventory>.sql \
  --identity-sha256 <exact-64-hex-sha>
```

The plan is `0001` through `0035`, then the exact `0036` and `0037` files, the pinned `0038_service_project_workbench.sql`, the pinned `0039_service_project_summary.sql`, and the supplied `0040_*.sql`. The historical migration pin file is `db-migration-pins.sha256`. The 0038 and 0039 hashes are pinned in `db-staging-common.sh` and must match their candidate manifests.

After apply, run the read-only role boundary check against the same loopback database.

```text
ops/service-project-staging/db-role-preflight.sh --user <staging-operator>
```

The role check verifies the five Canonical group roles remain `NOLOGIN` and `NOBYPASSRLS`, the binder can issue tickets, the app can redeem tickets, the workbench role can execute the summary, and the workbench role has no direct table `SELECT`. Login roles, credentials, provider mappings, and employee/customer grants require a separately approved secret and identity operation. They are never generated by these scripts.

The apply script stops on the first SQL or ledger error. A failed run leaves a partial database and refuses an in-place retry. Preserve the evidence and restore a newly created empty staging database before rerunning. There is no destructive cleanup command in this package.
